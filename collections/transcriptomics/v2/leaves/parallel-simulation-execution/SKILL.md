# parallel-simulation-execution

## Summary

Execute large fault-injection simulation sweeps for DNA storage pipelines by exploiting FrameD's transparent MPI parallelism plus batch-level job fan-out, so that the many sequencing reads and many fault-injection iterations required for pipeline comparison are computationally tractable.

## When to use

Use when fault-injection simulation sweeps over DNA storage pipelines produce too many sequencing reads and iterations to run serially, and results must be collected across many independent jobs.

## When NOT to use

- Small encoding/decoding exercises or quick pipeline tests on a single workstation — use the examples/small subshell background-job runner instead of full batch parallelism
- When the target HPC scheduler is not LSF and you have not yet extended the job-launch class in tools/lsf/submit.py (e.g. for SLURM or Cobalt)

## Inputs

- JSON fault-injection configuration files (e.g. examples/DNArSim/*.json, examples/iid/*.json)
- C-shell job-generation scripts that feed the JSONs to the job submission tools
- HPC batch scheduler environment (IBM LSF by default) with an MPI implementation installed

## Outputs

- Per-leaf-directory fault-injection statistics, JSON result files, and human-readable fi.stats files
- A consolidated Pandas dataframe (e.g. fault_injection_dataframe) generated by tools/data_analysis/db_gen.py

## How to apply

Configure the fault-injection test bed with JSON configuration files (as in examples/DNArSim and examples/iid) and let FrameD transparently parallelize the large number of sequencing reads and fault-injection iterations. At scale, use the job generation tools to launch all 240 independent simulations as batch jobs — FrameD assumes an IBM LSF-managed platform by default, with job-launch support for other schedulers (e.g. SLURM, Cobalt) added by extending the LSFJob/TcshJob class in tools/lsf/submit.py. On commodity hardware, use the examples/small runner instead, which emulates HPC job submission by spawning subshell background processes using 12 cores, requiring only an MPI implementation. MPI parallelism was tested with Intel MPI 2017 Update 1 and Open MPI 4.1.5; a pre-built Docker image (kvolkel/framed) replicates the environment with openmpi. After runs complete, compile statistics from each leaf directory's fi.stats files into a single Pandas dataframe with db_gen.py before analysis.

## Related tools

- **FrameD** (Simulation infrastructure that transparently parallelizes sequencing reads and fault-injection iterations via MPI and batch-level parallelism) — https://github.com/dna-storage/framed
- **DNArSim** (Nanopore channel simulator whose output supplies the sequencing reads consumed by the parallel fault-injection runs) — https://github.com/BHam-1/DNArSim

## Examples

```
cd $DNASTORAGE_HOME && tcsh examples/small/run_small.csh
```

## Evaluation signals

- All 240 independent simulations launched by the C-shell job-generation scripts complete and produce output in their leaf directories
- Each leaf directory contains a human-readable fi.stats file with fault-injection statistics
- db_gen.py produces a single Pandas dataframe covering all run configurations for a given fault-injected file
- The compiled dataframe reproduces the figures in notebooks/framed.ipynb using the raw pickle data (framed_DNArSim.pickle / framed_iid.pickle)
- MPI execution runs under Intel MPI 2017 Update 1 or Open MPI 4.1.5, or the provided Docker image, without environment failures

## Limitations

- The full data-generation configuration is only tractable on HPC systems and, as shipped, only works on HPC systems with an LSF scheduler; other schedulers require code extension
- Encoding or decoding large files may perform poorly on a standard computer, necessitating a more capable system
- The Docker image uses openmpi instead of the Intel MPI used for the original fault-injection simulations, introducing a minor environment difference
