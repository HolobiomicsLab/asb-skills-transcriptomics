# parameter-sweep-orchestration

## Summary

Orchestrates FrameD fault-injection parameter sweeps by parsing a JSON configuration (encoder, decoder, fault distribution, copy distribution, and optional sweep), expanding it into one simulation job per parameter combination, and collecting the per-combination statistics for cross-configuration comparison.

## When to use

Use when a DNA storage fault-injection experiment must vary encoder/decoder/fault/copy parameters systematically and each combination needs its own reproducible output directory with aggregated statistics.

## When NOT to use

- A single fixed configuration is needed with no parameter variation — run the pipeline once rather than setting up a sweep
- The error model is a nanopore channel with memory rather than the fault distributions FrameD injects directly — in that case FrameD wraps DNArSim output, but DNArSim itself is invoked separately via its Julia simulator

## Inputs

- JSON experiment configuration file (.json) specifying encoder, decoder, fault distribution, copy distribution, and optional parameter sweep
- Input data file to be encoded into DNA oligos
- Number of copies per oligo and number of fault injection iterations per parameter combination

## Outputs

- One output directory per parameter combination containing the parameter record (json) files for that run
- Human-readable 'fi.stats' file per leaf directory with aggregated counters (decode failures, byte-error and base-error locations)
- Optionally, a Pandas dataframe generated by tools/data_analysis/db_gen.py compiling all configurations

## How to apply

Parse the experiment's .json configuration file to extract encoder parameters, decoder parameters, fault distribution parameters, copy distribution parameters, and any optional parameter sweep. Encode the input data file into DNA oligos with FrameD's core encoding module, then for each expanded parameter combination generate the configured number of copies per oligo and sample errors according to the fault distribution, exploiting FrameD's transparent MPI/batch-level parallelism. Launch jobs through the job-generation tools (C-shell scripts calling the LSF submission infrastructure); on non-HPC machines use the examples/small subshell-background mode instead. Decode the error-carrying oligos back to the original data, recording decode failures and byte-error/base-error locations in per-parameter record files, and aggregate per-parameter counters into a 'fi.stats' file in each leaf output directory.

## Examples

```
python db_gen.py --path <top result path> --name fault_injection_dataframe
```

## Evaluation signals

- Every parameter combination produces its own output directory containing both a json parameter record and a 'fi.stats' statistics file
- Each fi.stats file contains aggregated counters including decode failures and byte-error and base-error locations
- The total number of launched jobs matches the expanded sweep size (e.g., the paper's example configurations launch all 240 simulations)
- python db_gen.py --path <top result path> --name fault_injection_dataframe yields a loadable Pandas dataframe at the top result path
- Figures regenerating from the dataframe via notebooks/framed.ipynb match the paper's published figures given the raw pickled data

## Limitations

- Batch-level job submission assumes an IBM LSF-managed HPC platform; other schedulers (Slurm, Cobalt) require extending the LSFJob/TcshJob class in tools/lsf/submit.py
- The paper's full example configurations (240 simulations) are only tractable on HPC systems; commodity-hardware runs must use the examples/small subshell mode
- Parallelism requires an installed MPI implementation (tested with Intel MPI 2017 and Open MPI 4.1.5) and sufficient cores or an HPC system
